# 모니터링 / 알람

> **알람이 없으면 이 설계는 성립하지 않는다.** (AADC-POC.md 7-③절)

WAS 장애 시 GSLB 를 옮기지 않기로 했으므로, backup 경유 상태는 "잠깐 버티는
생명줄"이 아니라 **사람이 고칠 때까지 지속되는 운영 상태**다.

그리고 그 상태는 **조용하다.** 서비스는 되고 조금 느릴 뿐이다. 사람이 고치는
것을 전제한 설계인데 아무도 모르면 몇 주도 간다. 자동 전환을 포기한 대가로
탐지를 강하게 만드는 것이 이 디렉터리다.

---

## 필수 알람 5종

| # | 조건 | 주기 | 의미 |
|---|---|---|---|
| ① | `/health/local` 실패 | **즉시** | backup 으로 넘어감, WAS 수리 필요 |
| ② | L4 backup 멤버 active 지속 | 시작 즉시 + **1시간마다** | 경과 시간과 함께 반복 알림 |
| ③ | semi-sync → async 강등 | 즉시 | **RPO 깨짐** |
| ④ | 복제 지연 임계 초과 | 즉시 | DR RPO 악화 |
| ⑤ | 점검 전용 VS 실패 | 즉시 | backup 경로 자체가 죽음 |

**①② 가 이 정책의 생명선이다.**

| 파일 | 실행 | 내용 |

설치: `install/40-monitor.sh`, 수신처: `/etc/aadc/monitor.env`

## 같은 알람을 1분마다 반복하지 않는다

`edge_alarm()` 이 **상태가 바뀐 순간에만** 보낸다. 상태는
`/var/lib/aadc-monitor/<키>.state` 에 남는다.

예외가 ② 다. degraded 는 **계속 울려야 한다** — 조용해서 잊히는 것이 이
상태의 위험이므로, 시작 시 한 번 + 이후 1시간마다 **경과 시간과 함께** 반복한다.
해제될 때 총 지속 시간을 남긴다.

---

## 검증 FQDN 이 따로 있는 이유

GSLB 1% 만으로는 야간에 DC-400 이 몇 시간씩 검증 공백에 빠진다. 초당 10건
기준 1% 면 0.1건/s 이고, 트래픽이 없는 시간대에는 0 이다.

`web1.example.com` / `web2.example.com` 로 각 DC 를 **가중치와 무관하게**
1분마다 직접 때린다.

## 점검 전용 VS 가 따로 있는 이유

backup 멤버는 평시 트래픽이 **0** 이라 검증되지 않는다. 장애 순간에야 동작
여부를 알게 된다. 교차 멤버만 담은 가상 서버를 하나 더 만들고 1분마다 호출한다.

⑤ 가 울린다는 것은 **"장애 시 넘어갈 곳이 이미 없다"**는 뜻이다.

## 임계값은 C1 이후에 확정한다

`/etc/aadc/monitor.env`

```ini
REPL_LAG_WARN_S=30        # ④ DCI RTT 실측 후 조정
DEGRADED_REPEAT_S=3600    # ② 1시간
```

7-④ 절 판정표에 따라 **degraded 허용 시간**을 정하고 운영 기준에 박아 둔다.

| DCI RTT | degraded 추가 지연 (N=10) | 판단 |
|---|---|---|
| 1~3ms | +11~33ms | 며칠도 운영 가능 |
| 5~10ms | +55~110ms | 반나절 정도 수용 |
| 20ms+ | +220ms 이상 | 수 시간 내 복구 필수 — SLA 명시 |
