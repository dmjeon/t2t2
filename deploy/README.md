# 카나리 배포

설치가 끝난 뒤에 쓰는 것이다. 핵심 설치(`install/00`~`30`)와는 무관하며,
`install/20-was.sh` 를 다시 돌리는 것으로 대체하지 않는다.

```bash
# ① DC-400 의 WAS 에서 먼저
./deploy-canary.sh 1.1.0

# ② 게이트 통과할 때까지 관찰  (최소 10~30분 또는 요청 500건 중 늦은 쪽)

# ③ 이상 없으면 DC-500 의 WAS 에서
./deploy-canary.sh 1.1.0
```

---

## 왜 이 순서인가

WAS 전멸은 토폴로지로 막을 수 없는 유일한 케이스다. 원인을 따져보면 답이 나온다.

| 원인 | 확률 | 막을 수 있나 |
|---|---|---|
| 독립적 동시 하드웨어 장애 | 매우 낮음 | 토폴로지로 이미 최선 |
| **공통 원인 — 잘못된 배포** | **높음** | **절차로 막음** |
| 공통 원인 — 스키마·설정 배포 | 중간 | 절차로 막음 |

**현실에서 WAS 전멸은 배포로 일어난다.** 양쪽에 같은 깨진 코드를 올리면
이중화가 아무 의미가 없다. GSLB 99:1 구조가 그대로 카나리가 된다.

```
1. DC-400 에 먼저 배포        ← 실트래픽 1% 가 즉시 검증
2. 관찰 (에러율 / p95 / 로그)  ← 영향받는 것은 1% 뿐
3. 이상 없으면 DC-500 배포
4. 문제 발견 시 DC-400 만 롤백  ← 99% 는 애초에 노출되지 않음
```

GSLB 1% 는 원래 "대기 경로 상시 검증"이 목적이었는데, 배포 카나리라는 두 번째
용도가 따라왔다. 그리고 이것이 WAS 전멸의 최대 원인을 실질적으로 막는다.

---

## 게이트를 반드시 둘 것

2단계를 눈대중으로 넘기면 절차 전체가 무의미해진다.

```
최소 10~30분  또는  요청 500건   중 늦은 쪽
```

1% 면 초당 10건 기준 **0.1건/s** 다. 통계적으로 의미 있는 표본이 쌓이는 데
시간이 걸린다. "5분 봤는데 괜찮더라"는 아무것도 보지 않은 것과 같다.

관찰 항목:

```bash
# 에러율 — WEB-DC2 에서
tail -f /var/log/nginx/aadc.log

# p95
../verify/05-scenario-c8-c11.sh c9a 1800

# 두 DC 의 버전 대조
curl -s https://web1.niceci.cloud/api/version    # DC-500
curl -s https://web2.niceci.cloud/api/version    # DC-400
```

---

## 스크립트가 하는 일

1. DC-500 이면 **먼저 묻는다** — DC-400 검증을 마쳤는지
2. 현재 코드를 `/opt/aadc/rollback/<버전>-<시각>` 에 복사 (롤백 지점)
3. 코드 교체 + `requirements.txt` 반영 + `AADC_APP_VERSION` 갱신
4. 재시작 후 `/api/version`, `/health/local`, `/health/deep` 확인
5. 하나라도 실패하면 **롤백 명령을 그대로 출력하고 종료**

롤백은 자동으로 하지 않는다. 배포 실패의 원인을 보지 않고 되돌리면 같은 일이
반복된다. 명령은 출력해 두되 누르는 것은 사람이 한다.
